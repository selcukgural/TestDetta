Limitations

Where {{name}} cannot see something, it selects more. This page lists those places, so you know when a selection is wider than it needs to be, and the few cases where a hand-written pattern can hide a test.

Test frameworks and runners

Both dotnet test runners are supported. The runner is read from global.json ("test": { "runner": "Microsoft.Testing.Platform" }, required for xUnit v3 on the .NET 10 SDK).

Each test project is built and run in the directory of the nearest global.json at or above it, so a file kept next to the solution (src/global.json) counts as it does for a developer there. --dry-run prints such commands as (cd src && dotnet test ...).

Recording and selection are tested end to end with xUnit v2 (VSTest), xUnit v3 and TUnit (Microsoft.Testing.Platform), and MSTest and NUnit under both runners, including projects that turn on their framework's own parallelization.

Tests that fail while recording

Test classes that fail while recording are always selected when their project is affected: a failing test stops early, so its coverage is incomplete.

When tests fail and no TRX report says which (NUnit under Microsoft.Testing.Platform without Microsoft.Testing.Extensions.TrxReport), the map is not used and selection falls back to names.

Maps recorded by an earlier version

A map holds what the recorder of its version could see. When a version of {{name}} records something differently in a way the map cannot show, it raises the map format, and maps of an earlier format are ignored: their test projects are selected by names, as without a map, which selects more, until the maps are recorded again. The first recording on the default branch after upgrading writes new maps; pull requests that run before it select more than they need to.

Maps recorded by {{name}} 0.1.x are of format 2 and are ignored by later versions. A test that builds a fixture type itself (new StoreFixture()) now keeps the rest of its code in its own class; a format 2 map could credit that code to the fixture's users and miss the test. The recorder now also notes which classes read a type's shape through reflection or a JSON schema (its attributes, properties and base types), so a change to that metadata selects them; a format 2 map has no such record.

Code that runs once per process

Caches, lazy singletons and EF model building run once per test process, and are credited to the first test class that triggers them. Changes to code that ran inside a static constructor or a cache-filling call (ConcurrentDictionary.GetOrAdd, Lazy<T>.Value, LazyInitializer, ConditionalWeakTable, IMemoryCache.GetOrCreate), are traced by name instead. A value kept in a field, such as a lazy singleton (_x ??= new X()), is credited to every test class that reads the field.

A cache written by hand, such as a Dictionary checked with TryGetValue, can still hide its users. Keep running the full suite on the default branch; recording does that.

State one test class leaves for the next

A test class can behave differently depending on what an earlier class in the same process left behind, such as a global configuration it set and never reset. The map records the path the class took in the recorded order, so a change to the code it would run alone or in another order may not select it. The full run in the same order does not fail it either. In the corpus this hid one change in {{corpusFailingChanges}} (NLog's LogManagerTests). Tests that reset shared state in their setup avoid it.

Project files

Project files are evaluated by MSBuild (one dotnet msbuild call, cached in .testdetta/cache) for references, compiled and embedded items, assembly names and target frameworks, in the default configuration and without a restore.

  • Items only a package's props add, or only a Release condition adds, are not seen.
  • A project MSBuild cannot evaluate is read as XML, as are imports.
  • A changed file inside a project folder that the project does not compile counts as a change to that project: the project runs completely when its build uses the file, and only the tests that read it when the build does not (see files the build does not use). A file outside every project folder selects only the tests that read it; see files outside every project.
  • Test projects are also recognised by a *.Tests or *.Test name.

What the code cannot show

{{name}} sees your source code, your project files and what your tests ran while recording. It cannot see:

  • External services and databases. A change in another system, such as a schema migration applied elsewhere or an API your tests call, selects nothing here.
  • Files read by native code or by programs that are not .NET, and files read through a .NET API outside the recorded list. Reads by your own code and by the .NET libraries your tests use are recorded; see files the build does not use.
  • Programs started by third-party code that are not .NET (Core), such as a native or .NET Framework executable of your repository that a process library starts. .NET processes are recorded whoever starts them, and so are starts by your own code.
  • Environment: variables, machine settings and installed tools that differ between runs.

Package version changes are seen: a PackageVersion change in Directory.Packages.props runs the projects that reference the package, and a PackageReference change is a change to the project file.

Preprocessor symbols

C# files are parsed with each target framework's real preprocessor symbols, and also with no symbols and with every symbol their #ifs name, so code under any active condition is seen.

Target frameworks

For a test project that targets several frameworks, what is selected depends on the frameworks the tests run for. The same change can select more tests in one run and fewer in another:

  • More, for frameworks the map was not recorded for. A map holds one framework's run. When the tests also run for another framework, a change that alters what that framework's build compiles or generates (source generator output, files the build reads) runs the test project completely. Record without -f, or run the tests with the same -f; see What runs everything.
  • Fewer, with -f. A run for one framework loads only that framework's builds. A change compiled only for other frameworks (code under an #if that framework leaves out, such as a polyfill for .NET Framework 2.0) selects nothing in that run, when the changed project and every project between it and your test projects target that framework. Without -f, the same change selects the tests that may run it.

So a CI job that runs one framework can skip tests that only another framework's build could fail. If your test projects target several frameworks, run every framework somewhere, for example in a nightly full run.

Skipped tests

Tests skipped while a map was recorded have no coverage. A class whose tests were all skipped is selected on another platform, where it may run, and skipped on the recording platform. Tests skipped for other reasons, such as a missing Docker daemon, are covered only by recording where the tests run.

Source generators

Code written by source generators is not in the source tree. td record reads it from the PDBs of the recorded assemblies (portable or embedded) and keeps the names it mentions in the map, so name tracing sees generated callers. Assemblies built without a portable PDB give nothing.

F#

F# code is analysed like C#, and so is Visual Basic. F# signature files (.fsi) are not: a change to one runs everything that depends on its project. A change to an inline function is traced by name to its callers, because the compiler copies its body into them and a coverage map credits them instead.
