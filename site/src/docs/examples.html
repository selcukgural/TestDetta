The change

A rename in the declarative configuration package: the flag that says whether OTEL_CONFIG_FILE is overridden gets a name that says so. It changes no behaviour, but it is a code change, so a normal pipeline would build and run every test project in the repository.

How the decision was made

{{name}} follows the change from the file to the tests that can observe it. The changed method is private; only UseDeclarativeConfiguration calls it. The coverage map, recorded on main, knows which test classes ran it: 8 classes in one test project. The other 266 ran none of it and name none of it.

Were those the right 8?

To check, we made WarnIfConfigFileEnvVarDiffers throw and ran the whole solution: 6,078 tests in 19 test projects. 70 tests failed, in exactly the 8 classes {{name}} selected: nothing missed, nothing extra. Across 40 repositories

One change is one data point. To know how {{name}} behaves on code it has never seen, we run it on 40 open-source .NET libraries and check every selection against the tests that really fail.

  1. RecordA coverage map at the head of the default branch.
  2. Change one memberUp to 100 sampled methods, properties and constructors, one at a time.
  3. Break it and run everythingThe member throws, and the whole suite runs to see which classes fail.
  4. Check the selectionEvery failing class must be one {{name}} selected. A miss is confirmed by running the class alone.

Where it gains most

Layered code, where each test reaches a small part of the system, gains most: Polly ran 3% of its test classes per change, Spectre.Console 6%, OpenTelemetry .NET 8%. Libraries where nearly every test runs the same core gain little: Mapperly 97%, NLog 96%, AutoMapper 85%. There, a change to the core really does reach most tests, and {{name}} runs them. LibGit2Sharp ran everything (100%): a reference that depends on the target framework keeps {{name}} conservative there.
