What runs everything

Most changes select a few test classes. Some cannot be narrowed down safely, so {{name}} runs a whole test project, or every project below a folder. This page lists them all, so a wide selection never comes as a surprise.

Build-wide files

These files change how every project below them builds. A change to one of them runs every test project in its folder and below it:

FileRuns
Directory.Build.props, Directory.Build.targets, Directory.Build.rspEvery test project below it
Directory.Solution.props, Directory.Solution.targetsEvery test project below it
global.json, NuGet.config, .editorconfigEvery test project below it
Directory.Packages.props, only PackageVersion items changedOnly the test projects that reference a changed package, and those that depend on them
A changed source generator, for a test project that has no coverage map, builds without a portable PDB, or was recorded with -f for one of several frameworksWhat it generates is compared from a build, and here there is nothing to compare. Otherwise only the generated code that changed counts.
A project referenced with ReferenceOutputAssembly="false"The tests may run it as another process, which coverage does not see.

Changes that run a whole test project

ChangeWhy it cannot be narrowed
The project file, or a .props or .targets file it importsIt can change how anything in the project builds.
Any file in the project that is not C#, such as appsettings.json, a .resx or a test data fileNo coverage map says who reads it.
A global using or an assembly attributeIt applies to every file.
A C# change in code no declaration covers, for example under a preprocessor conditionThere is no member to follow.
A changed type that nothing names, but that a framework could discover through reflection (controllers, message handlers, EF configurations)Names and coverage cannot tell who finds it.
A change in an F# or Visual Basic projectTheir code is not analysed.
A project used as an analyzer or source generatorIts effect is on compilation, not on calls.

Each of these also runs every test project that depends on the one affected.

Coverage map situations

  • An older map and build changes in between. When the map is a few commits older than your merge base and a build file or a configuration file changed in between, the affected test projects run completely. --drift-fallback name decides them by name instead. See the drift bridge.
  • Every class selected. A project whose classes are all selected runs without a filter.
  • A filter that matches nothing. The project runs again without the filter, and {{name}} treats it as its own bug.

No map at all does not run everything: selection falls back to tracing by name, which is wider than coverage but still narrow.

Files outside every project

A changed file outside every project folder, such as README.md, files under .github/ or test data at the root of the repository, belongs to no project. If a test read it by a path while the coverage map was recorded, a change to it, or a new file in a folder a test listed, runs the test classes that read it. A read outside any test, in a fixture's setup or while initializing something the tests share runs the whole test project. A file no recorded test read selects nothing. The output counts these files as read by recorded tests or read by none.

Reads are recorded in the code of the repository's own projects, not inside third-party libraries (a snapshot library reading its .verified files, for example), and only in coverage maps recorded by a version that records them. Keep files read that way inside the test project, or list them as its items, for example <None Include="..\..\testdata\**" CopyToOutputDirectory="PreserveNewest" />. Then the file belongs to the project wherever it lives, and changing or deleting it runs the project.

One exception: a source or build file that no project claims (.cs, .fs, .vb, .props, .targets, .projitems) counts as a build input of every project whose imports could not be fully resolved, so those run.
