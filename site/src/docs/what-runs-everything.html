What runs everything

Most changes select a few test classes. Some cannot be narrowed down safely, so {{name}} runs a whole test project, or every project below a folder. This page lists them all, so a wide selection never comes as a surprise.

Build-wide files

These files change how every project below them builds. A change to one of them runs every test project in its folder and below it:

FileRuns
Directory.Build.props, Directory.Build.targets, Directory.Build.rspEvery test project below it
Directory.Solution.props, Directory.Solution.targetsEvery test project below it
global.json, NuGet.config, .editorconfigEvery test project below it
Directory.Packages.props, only PackageVersion items changedOnly the test projects that reference a changed package, and those that depend on them
A changed source generator, for a test project that has no coverage map, builds without a portable PDB, or was recorded with -f for one of several frameworksWhat it generates is compared from a build, and here there is nothing to compare. Otherwise only the generated code that changed counts.
A changed project referenced with ReferenceOutputAssembly="false", when the referencing project's build turns its output into code it compiles, or the test project's map does not record which tests start or load it, or the test project targets several frameworks and its map holds the build of only one of the frameworks the tests run for (recorded with -f; record without it, or run the tests with the same -f)Otherwise only the test classes that started it as a process or loaded it while the map was recorded run, and a reference only for build order runs nothing.

The project file, or a .props or .targets file it importsIt can change how anything in the project builds.

With --non-code-files project, any file in the project that is not codeIt changes what the build produces. Files the build does not use run only their readers (below).

Each of these also runs every test project that depends on the one affected.

Files in a project that the build does not use

A README.md, a CHANGELOG.md or a data file the tests read from the source tree changes no build output. Under the default --non-code-files readers, a change to such a file runs only the test classes that read it while the coverage map was recorded, in any test project; a read outside any test, in a fixture's setup or while initializing something the tests share runs that test project completely, and a file no recorded test read runs nothing. A file counts as unused by the build when MSBuild lists it as a None item without CopyToOutputDirectory and no build item type (Compile, EmbeddedResource, Content, AdditionalFiles, Protobuf, the WPF, MAUI and Android items) lists it, and no MSBuild file of the repository names it outside comments and package metadata, includes it in an item of another type, or has a target that walks every None item.

Reads are recorded in your own code and in the libraries your tests use, a snapshot library reading its .verified files for example. A test project still runs completely for such a file when it has no map, or its map was recorded before {{name}} recorded the reads of libraries, or a library could not be rewritten to show its reads (the output names it).

What this cannot see: a file read by native code, by a program that is not .NET, or through a .NET API outside the recorded list (ZipFile.OpenRead, an X509Certificate2 from a path); and a build step of an SDK or a package that processes files under an item type of its own that is not in the list above. If your build or tests use files that way, choose --non-code-files project (action input non-code-files: project): every non-code file then runs its project and the projects depending on it, as before.

Coverage map situations

  • An older map and build changes in between. When the map is a few commits older than your merge base and a build file or a configuration file changed in between, the affected test projects run completely. --drift-fallback name decides them by name instead. See the drift bridge.
  • Every class selected. A project whose classes are all selected runs without a filter.
  • A filter that matches nothing. The project runs again without the filter, and {{name}} treats it as its own bug.

No map at all does not run everything: selection falls back to tracing by name, which is wider than coverage but still narrow.

Files outside every project

A changed file outside every project folder, such as README.md, files under .github/ or test data at the root of the repository, belongs to no project. If a test read it by a path while the coverage map was recorded, a change to it, or a new file in a folder a test listed, runs the test classes that read it. A read outside any test, in a fixture's setup or while initializing something the tests share runs the whole test project. A file no recorded test read selects nothing. The output counts these files as read by recorded tests or read by none.

Reads are recorded in your own code and in the libraries your tests use, and only in coverage maps recorded by a version that records them. A file read in a way TestDetta cannot see (native code, a program that is not .NET) is safest listed as an item of the test project, for example <None Include="..\..\testdata\**" CopyToOutputDirectory="PreserveNewest" />. Then the file belongs to the project wherever it lives, and changing or deleting it runs the project.

One exception: a source or build file that no project claims (.cs, .fs, .vb, .props, .targets, .projitems) counts as a build input of every project whose imports could not be fully resolved, so those run.
