GitHub Actions

Zeichnen Sie für jeden Commit auf dem Standard-Branch eine Map auf, und lassen Sie Pull Requests nur die Tests ausführen, die ihre Änderungen betreffen. Die Action baut {{name}} selbst und legt die Maps im Actions-Cache ab.

Workflow

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  actions: read # lets pull requests find the newest coverage map in the Actions cache

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7 # pin to a commit SHA
        with:
          fetch-depth: 0 # TestDetta compares with the merge base
          persist-credentials: false

      - uses: actions/setup-dotnet@v6 # pin to a commit SHA
        with:
          global-json-file: global.json

      # Also the full test run of main. Leave out projects that cannot run here, such as
      # integration tests that need a database; they are then decided by name on pull requests.
      - if: github.event_name == 'push'
        uses: <owner>/testdetta@<sha>
        with:
          mode: record
          projects: |
            tests/Shop.Tests/Shop.Tests.csproj

      - if: github.event_name == 'pull_request'
        uses: <owner>/testdetta@<sha>
        with:
          mode: test
          dotnet-test-args: --logger trx
          license: ${{ secrets.TESTDETTA_LICENSE }}

Die vollständige Historie ist erforderlich. Bei einem Shallow Clone bricht die Action mit einem Fehler ab. Checken Sie mit fetch-depth: 0 aus.

Wie die Maps zu den Pull Requests gelangen

  • Der Record-Modus speichert die Maps im Actions-Cache unter testdetta-coverage-<commit>. Pull Requests können die Caches ihres Basis-Branches lesen.
  • Ein Pull Request verwendet die Map seiner Merge-Base oder die neueste, die bis zu max-map-age First-Parent-Commits davor aufgezeichnet wurde.
  • Um eine solche nicht exakt passende Map zu finden, werden die Caches des Repositorys aufgelistet, was actions: read erfordert. Ohne diese Berechtigung wird nur eine Map an der Merge-Base gefunden, und der Schritt weist in einem Hinweis darauf hin.
  • Ganz ohne Map funktioniert mode: test trotzdem und entscheidet nur anhand von Namen.

Wenn bei der Aufzeichnung Tests fehlschlagen, wird die Map trotzdem gespeichert, bevor der Job fehlschlägt, sodass Pull Requests weiterhin eine Map zur Verfügung haben.

Berechtigungen

Shadow-Modus

Um {{name}} auszuprobieren, ohne etwas auszulassen, verwenden Sie mode: shadow in Pull Requests. Jeder Test, den Ihr Befehl ausführt, läuft, und das Ergebnis des Jobs ist das dieses Laufs; die Job Summary und das Bericht-Artefakt zeigen, was die Auswahl ausgeführt hätte, die gemessenen Minuten und jede fehlgeschlagene Klasse, die sie ausgelassen hätte. Das Artefakt heißt testdetta-shadow-<run>-<attempt>-<job>-…, eins pro Job und Matrix-Eintrag (shadow-artifact-suffix fügt Ihren eigenen Teil hinzu), und wird 90 Tage aufbewahrt. Nennen Sie Ihre Solution in dotnet-test-args, damit sie als ein Befehl läuft wie in Ihrem eigenen Job; siehe td test --shadow.

Er braucht keine Lizenz, daher wird ihm das Lizenz-Secret nicht übergeben, und {{name}} selbst macht im Shadow-Modus keinen Netzwerkaufruf. Die Action lädt das {{name}}-Paket von nuget.org herunter (gegen seinen SHA-512 geprüft) und listet die Maps in Ihrem Actions-Cache auf und stellt sie wieder her, wie im Test-Modus. Kein Schritt vor den Tests lässt den Job scheitern: Kann einer seinen Teil nicht erledigen (ein Shallow Checkout, der Download, ein fehlender Basis-Branch, eine ungültige Eingabe) oder endet {{name}} ohne ein Ergebnis der Tests, führt der Schritt stattdessen Ihr einfaches dotnet test mit denselben Argumenten aus, und die Job Summary nennt den Grund. Ein Paket, das nicht zu seiner Prüfsumme passt, wird nie ausgeführt. Auch ein fehlgeschlagener Upload des Berichts lässt den Job nie scheitern.

      - if: github.event_name == 'pull_request'
        uses: <owner>/testdetta@<sha>
        with:
          mode: shadow
          dotnet-test-args: Shop.slnx

Audit nach Zeitplan

Um die Auswahl an Ihrem eigenen Code zu prüfen, verwenden Sie mode: audit nach Zeitplan, etwa wöchentlich auf dem Branch, den der Record-Modus aufzeichnet. Es bricht Member Ihres Codes Änderung für Änderung in einer Kopie des Arbeitsbaums, führt jeden Test aus, der eine Änderung sehen kann, und prüft, dass die Auswahl jede fehlgeschlagene Testklasse ausgeführt hat; siehe td audit. Ihr Checkout und seine Build-Ausgabe werden nur gelesen. Die Job-Zusammenfassung zeigt das Ergebnis und jedes Verfehlen mit seiner Entscheidungskette; das Artefakt testdetta-audit-<run>-<attempt> bewahrt den JSON-Bericht 90 Tage auf. Es verwendet die neueste Map innerhalb von max-map-age des Commits, auf dem es läuft. Es braucht keine Lizenz und macht keinen Netzwerkaufruf, daher wird ihm das Lizenz-Secret nicht übergeben. Es läuft stundenlang auf Ihren Runnern: Geben Sie dem Job ein timeout-minutes deutlich über audit-budget, denn eine Änderung, die beim Ende des Budgets noch läuft, läuft erst zu Ende.

on:
  schedule:
    - cron: '0 3 * * 1' # Mondays, 03:00 UTC
  workflow_dispatch:

permissions:
  contents: read

jobs:
  audit:
    runs-on: ubuntu-latest
    timeout-minutes: 300
    permissions:
      contents: read
      actions: read # finds the newest coverage map in the Actions cache
    steps:
      - uses: actions/checkout@v7 # pin to a commit SHA
        with:
          fetch-depth: 0
          persist-credentials: false

      - uses: actions/setup-dotnet@v6 # pin to a commit SHA
        with:
          global-json-file: global.json

      - uses: <owner>/testdetta@<sha>
        with:
          mode: audit
          audit-budget: 4h

Ein Lauf mit mindestens 100 Änderungen, die Tests gebrochen haben, und keinem Verfehlen bringt die obere 95-%-Schranke der Verfehlensrate auf höchstens 3,0 % (die Schranke wird aufgerundet angezeigt).

Job Summary

Im Test-Modus schreibt {{name}} seine Auswahl in die Job Summary: die geänderten Dateien und die Basis, mit der verglichen wurde, jedes Testprojekt mit der Angabe, ob es gefiltert, vollständig oder gar nicht lief und warum, die Testergebnisse sowie den Lizenzstatus, wenn er relevant ist. Pfade, Klassennamen und Gründe aus dem Repository werden als Code geschrieben, sodass Dateinamen in einem Pull Request keine Links oder Erwähnungen in die Seite einschleusen können.

Nur einen Teil der Testsuite aufzeichnen

Die Aufzeichnung führt die gesamte Testsuite einmal mit Coverage aus, was auf dem Standard-Branch zugleich Ihr vollständiger Testlauf ist. Projekte, die auf dem Runner nicht laufen können, etwa Integrationstests, die eine Datenbank benötigen, lassen Sie mit projects weg. Pull Requests entscheiden diese Projekte dann anhand von Namen.

Wenn ein früherer Schritt die Solution bereits mit derselben Konfiguration gebaut hat, setzen Sie no-build: true. Für eine Testsuite, die mehrere gleichzeitige Testprozesse verträgt, verteilt parallel die Testklassen jedes Projekts auf entsprechend viele Prozesse.
