CLI-Referenz

Alle Befehle, Optionen und Umgebungsvariablen, jeweils mit ihrer Funktion, ihrem Standardwert und einem Beispiel. Mit td --help erhalten Sie die Kurzfassung.

td affected [options]              Print the projects and tests a change affects
td test [options] [-- <args>]      Run only the tests a change affects
td record [options]                Run all tests with coverage and store the map
td license status [options]        Check the license and show what it covers
td license install <license|file>  Store a license in ~/.testdetta/license
td audit [options] [-- <args>]     Break your code on purpose and check the selection

Optionen für jede Analyse

Diese funktionieren mit affected, test, record und audit; audit vergleicht immer mit HEAD, daher gilt --base dort nicht.

--base <ref>

Die Git-Ref, mit der verglichen wird. {{name}} vergleicht Ihr Arbeitsverzeichnis mit der Merge-Base von HEAD und dieser Ref, sodass Commits, die nach Ihrer Abzweigung auf dem Basis-Branch gelandet sind, nicht als Ihre Änderungen zählen. Standard: origin/main.

td test --base origin/develop
td affected --base HEAD~3      # the last three commits and anything uncommitted

--repo <path>

Ein beliebiger Pfad innerhalb des zu analysierenden Repositorys. Standard: das aktuelle Verzeichnis.

td affected --repo ../shop

-v, --verbose und --log-level <level>

Logs gehen nach stderr, sodass stdout maschinenlesbar bleibt. -v aktiviert Debug-Logs, die jede Entscheidung erklären: warum ein Projekt betroffen ist, welchen Member eine Testklasse ausgeführt hat, welchem Namen eine Verfolgung gefolgt ist. --log-level wählt eine der Stufen trace, debug, information, warning (Standard), error oder none; trace ergänzt die unverarbeitete Git-Ausgabe.

td affected -v 2> testdetta-debug.log
td test --log-level information

--max-map-age <n>

Verwendet eine Coverage-Map, die bis zu n First-Parent-Commits vor der Merge-Base aufgezeichnet wurde, wenn es an der Merge-Base selbst keine gibt. Die Änderungen dazwischen werden überbrückt: Klassen, die einen seit der Map geänderten Member ausgeführt haben, der Ihre Änderung erreichen kann, werden ebenfalls ausgewählt. 0 verwendet nur eine an der Merge-Base aufgezeichnete Map. Standard: 50. Siehe Wie es entscheidet.

td test --max-map-age 20

--drift-fallback <all|name>

Legt fest, was geschieht, wenn die Änderungen seit einer älteren Map etwas enthalten, das sich nicht durch Member beschreiben lässt: eine Build-Datei, Konfiguration, ein globales Using. all (Standard) führt die betroffenen Testprojekte vollständig aus; name entscheidet sie anhand von Namen, was schneller ist, aber blind für Aufrufe, die über Konfiguration oder Reflection verbunden sind.

td test --drift-fallback name

--maps-dir <dir>

Bewahrt Coverage-Maps außerhalb des Repositorys auf, ein Ordner pro Commit. record speichert nach <dir>/<commit>/; affected und test stellen die neueste innerhalb von --max-map-age wieder her. Verwenden Sie die Option auf anderen CI-Systemen als GitHub Actions, mit einem gemeinsamen Laufwerk oder einem synchronisierten Objektspeicher. Standard: Die Maps liegen in .testdetta/coverage im Repository.

td record --maps-dir /srv/testdetta-maps/shop
td test --base origin/main --maps-dir /srv/testdetta-maps/shop

td affected

Gibt aus, was eine Änderung betrifft und warum, ohne Tests auszuführen. Es liest die Projektdateien über die Auswertung von MSBuild und baut nur mit --build.

--format <text|json|paths|commands>

FormatAusgabeVerwendung
text (Standard)Betroffene Projekte mit dem Grund, danach der TestplanZum Lesen
jsonJedes Projekt und jede Testklasse mit Entscheidung, Belegen und ZeitschätzungSkripte, Dashboards
pathsEine betroffene Test-.csproj pro ZeileAls Eingabe für ein anderes Tool
commandsEin dotnet test-Befehl pro Testprojekt, mit seinem FilterUm die Tests auf eigene Weise auszuführen
 
td affected --format json > plan.json
td affected --format paths | xargs -n1 dotnet build

--tests-only

Listet nur die betroffenen Testprojekte auf, nicht die Produktionsprojekte auf dem Weg dorthin.

--build

Erreicht eine Änderung einen Source Generator im Repository, werden die Testprojekte, die ihn verwenden, gebaut und sein erzeugter Code mit ihrer Coverage-Map verglichen, wie es td test immer tut. Ohne diese Option wird ein vorhandener Build gelesen, der neuer als die Quellen ist; gibt es keinen, werden diese Testprojekte als vollständig laufend aufgeführt.

td test

Baut und führt nur die betroffenen Tests aus: einen Filter pro Testprojekt, wenn nur einige Klassen betroffen sind, das ganze Projekt, wenn alle betroffen sind oder sich eine Änderung nicht eingrenzen lässt, und nichts, wenn keine betroffen ist. Exitcode 3, wenn ein Test fehlschlägt. Erreicht eine Änderung einen Source Generator im Repository, werden die Testprojekte, die ihn verwenden, zuerst gebaut, und nur geänderter erzeugter Code zählt; schlägt der Build fehl, endet der Befehl hier mit den Fehlern des Compilers.

--dry-run

Gibt die dotnet test-Befehle aus, statt sie auszuführen. Ein Projekt, dessen global.json in einem Unterordner liegt, wird als (cd src && dotnet test ...) ausgegeben.

--summary-file <path>

Hängt eine Markdown-Zusammenfassung an: das Ergebnis jedes Projekts, welche Klassen liefen und warum, welche übersprungen wurden und die eingesparte aufgezeichnete Testzeit. Verweisen Sie in GitHub Actions auf $GITHUB_STEP_SUMMARY; die Action erledigt das für Sie. Siehe ein Beispiel.

td test --summary-file "$GITHUB_STEP_SUMMARY"

--shadow

Shadow-Modus, um {{name}} auszuprobieren, ohne etwas auszulassen. Er braucht keine Lizenz, und {{name}} selbst macht darin keinen Netzwerkaufruf: Es wird keine Lizenz gelesen oder erneuert, und nichts wird gesendet. Ihre Builds stellen Pakete wie immer wieder her, und der erneute Lauf auf dem Basis-Commit stellt die Pakete dieses Commits wieder her wie jeder Build. Jeder Test, den Ihre eigenen ---Argumente ausführen, läuft, und der Exit-Code ist der dieses Laufs. Nennen sie eine Solution (.sln, .slnx, .slnf), ein Projekt, ein Verzeichnis oder nichts (die eine Solution oder das eine Projekt im Arbeitsverzeichnis), führt {{name}} genau diesen einen dotnet test-Befehl in Ihrem Arbeitsverzeichnis aus und fügt nur einen Testbericht pro Projekt hinzu: --logger trx unter VSTest, sofern Sie nicht selbst einen TRX-Logger angeben, oder die Berichtsoption der Testing Platform. Ihr Ergebnisverzeichnis, Ihre Logger und die Dateien, die Ihr Lauf schreibt, bleiben, wie sie sind: {{name}} liest die Berichte dort, wo sie landen, und kopiert sie, und löscht nur die Berichte, die es selbst angefordert hat (wenn Sie keinen eigenen TRX-Logger und keine eigene Berichtsoption angeben), sobald es sie gelesen hat. Andernfalls, etwa wenn es keine einzelne Solution zum Ausführen gibt oder zwei Testprojekte Assemblys mit demselben Namen bauen, läuft jedes Testprojekt, das Ihr Befehl ausführt, einzeln nacheinander aus demselben Verzeichnis, und der Bericht nennt den Grund. Lässt sich nicht feststellen, welche Testprojekte Ihr Befehl ausführt, läuft jedes Testprojekt unter seinem Verzeichnis, und auch das nennt der Bericht.

Scheitert {{name}}, bevor die Tests laufen, läuft Ihr Befehl unverändert ohne es; scheitert es danach, ist der Exit-Code trotzdem der dieses Laufs; in beiden Fällen nennt der Bericht den Grund, warum es kein Shadow-Ergebnis gibt. Danach vergleicht {{name}} den Lauf Test für Test mit dem, was es ausgewählt hätte, und führt jede fehlgeschlagene Klasse, die es ausgelassen hätte, erneut aus: allein mit der Änderung; besteht sie allein, mit den anderen Klassen ihres Projekts wie im vollständigen Lauf (besteht sie dort, ist sie instabil; schlägt sie erneut fehl, ist sie reihenfolgeabhängig); dann auf dieselbe Weise auf dem Basis-Commit, in einem eigenen Checkout. Schlägt jeder Test, der mit der Änderung fehlschlägt, dort ebenfalls fehl, hat die Änderung sie nicht kaputt gemacht; besteht dort einer, ist es ein Verfehlen. Eine Klasse, die nicht erneut laufen kann, zählt als Verfehlen, bis sie geprüft ist. Die erneuten Läufe schreiben ihre Berichte nur in den eigenen temporären Ordner von {{name}} und können den Job verlängern, höchstens um das Klassifizierungsbudget. Strg+C oder ein abgebrochener Job stoppt die Tests und entfernt diesen Ordner und den Basis-Checkout.

Vor dem Ende des vollständigen Laufs wird nichts über die Auswahl gezeigt, und Entscheidungen erscheinen nur für die Klassen, die in diesem Job gelaufen sind: Eine Klasse, die Ihr Filter ausgelassen hat, wird ohne Entscheidung als nicht gelaufen aufgeführt, die eigene Entscheidung des Projekts wird dann ebenfalls nicht gezeigt, und die Summen zählen nur, was gelaufen ist. Der Bericht nennt zuerst das Ergebnis mit der gemessenen Zeit des ganzen Laufs, dann, wie der Lauf gemacht wurde, die Entscheidung und das Ergebnis jeder Klasse, die gemessene Zeit pro Projekt neben dem Teil, den die Auswahl ausgeführt hätte, und was Sie brauchen, um das Ergebnis ohne Lizenz nachzuvollziehen: die Version von {{name}} und ihren SHA-256, die Commits, die Coverage-Maps und ihre Hashes sowie denselben td test --shadow-Befehl.

Grenzen: Berichte werden unter dem Repository und in Ihrem Ergebnisverzeichnis gesucht, daher wird ein Ergebnisverzeichnis, das in den Run Settings außerhalb des Repositorys festgelegt ist, nicht gelesen. Der Basis-Checkout liegt in einem temporären Ordner außerhalb des Repositorys, daher sind Dateien oberhalb der Repository-Wurzel (eine Directory.Build.props, global.json oder NuGet.config in einem übergeordneten Ordner) dort nicht sichtbar; eine Klasse, deren erneuter Lauf auf dem Basis-Commit nicht bauen kann, wird als nicht eingeordnet gemeldet. Ein Testprojekt auf der Testing Platform erhält seine Berichtsoption anhand seiner Build-Ausgabe (eine Option, die es nicht kennt, würde seinen Lauf scheitern lassen, daher wird keine aus Paketverweisen erraten): Wurde es vor dem Lauf nicht gebaut, läuft es ohne Bericht, und der Bericht nennt es mit "no test report: the project was not built before the run", sodass seine Fehlschläge nicht verglichen werden können. Bauen Sie zuerst und übergeben Sie --no-build, wie unten.

dotnet build MySolution.sln -c Release
td test --shadow --summary-file "$GITHUB_STEP_SUMMARY" -- MySolution.sln -c Release --no-build

--shadow-no-classify

Führt die fehlgeschlagenen Klassen, die die Auswahl ausgelassen hat, nicht erneut aus. Sie werden dann als nicht eingeordnet gemeldet.

--shadow-report <path>

Wohin der JSON-Bericht geschrieben wird. Standard: .testdetta/testdetta-shadow.json im Repository.

--shadow-analysis-timeout <time>

Wie lange die Analyse von {{name}} vor den Tests dauern darf. Standard: 10m. Danach wird die Analyse gestoppt, jeder Test läuft trotzdem, und der Bericht nennt den Grund, warum es kein Shadow-Ergebnis gibt.

--shadow-rerun-timeout <time>, --shadow-rerun-idle-timeout <time>

Wie lange ein erneuter Lauf mit der Änderung dauern darf und wie lange seine Prozesse fast keine CPU nutzen dürfen, bevor er als hängend gestoppt wird. Standard: 15m und 5m. Die Klassen eines gestoppten Laufs werden als nicht eingeordnet gemeldet.

--shadow-base-timeout <time>, --shadow-base-idle-timeout <time>

Dasselbe für den erneuten Lauf auf dem Basis-Commit, der in seinem Checkout zuerst wiederherstellt und baut. Standard: 30m und 10m; die Leerlaufgrenze ist länger, weil ein Restore auf das Netzwerk wartet, während die CPU fast stillsteht.

--shadow-classify-budget <time>

Wie lange die gesamte Einordnung dauern darf: alle erneuten Läufe und der Basis-Checkout zusammen. Standard: 45m. Ein laufender erneuter Lauf wird gestoppt, wo das Budget endet, und die bis dahin nicht eingeordneten Fehlschläge werden mit dem Grund als nicht eingeordnet gemeldet. Der vollständige Lauf und der Exit-Code sind nie betroffen. Der Bericht zeigt die verwendeten Grenzen und wie viel vom Budget verbraucht wurde.

Eine <time> ist 90s, 15m, 1h oder 1h30m, höchstens 168h; eine bloße Zahl bedeutet Minuten; 0 oder none bedeutet keine Grenze. In der GitHub Action setzen die gleichnamigen Eingaben (shadow-analysis-timeout, shadow-rerun-timeout, shadow-classify-budget usw.) sie.

td test --shadow --shadow-classify-budget 20m --shadow-base-timeout none

-- <dotnet test arguments>

Alles nach -- wird an jeden dotnet test-Aufruf übergeben. Ihr eigener --filter bleibt erhalten: {{name}} verknüpft ihn mit seinem Klassenfilter, sodass nur die ausgewählten Tests innerhalb Ihres Filters laufen. Trait-, Methoden- und Namespace-Filter von xUnit v3 schränken die Auswahl ebenso ein. Ein Filter, den der Runner nicht mit einem Klassenfilter verknüpfen kann (ein Klassen- oder Query-Filter von xUnit v3, ein Tree-Node-Filter von TUnit), lässt das Projekt vollständig unter Ihrem Filter laufen. Im Shadow-Modus sind sie Ihr eigener Testbefehl; siehe --shadow.

td test -- -c Release --logger trx
td test -- --no-restore
td test -- --filter "Category!=Integration"

td record

Führt alle Tests mit Coverage aus und schreibt eine Map pro Testprojekt nach .testdetta/coverage (oder --maps-dir). Führen Sie den Befehl auf Ihrem Standard-Branch aus; er ist zugleich der vollständige Testlauf dieses Branches. Exitcode 3, wenn Tests fehlschlagen; die Maps werden trotzdem geschrieben, und die fehlschlagenden Klassen werden später immer ausgewählt.

-c, --configuration <name>

Build-Konfiguration. Standard: Debug.

-f, --framework <tfm>

Das Ziel-Framework, das in einem Testprojekt mit mehreren Ziel-Frameworks aufgezeichnet wird. Standard: das erste Ziel-Framework des Projekts, das auf diesem Rechner läuft (.NET Framework nur unter Windows).

td record -f net10.0

--project <path>

Zeichnet nur dieses Testprojekt auf, relativ zum Stammverzeichnis des Repositorys; für mehrere Projekte wiederholen Sie die Option. Lassen Sie Projekte weg, die in der CI nicht laufen können, etwa Integrationstests, die eine Datenbank benötigen; sie werden dann anhand von Namen entschieden.

td record --project tests/Shop.Tests/Shop.Tests.csproj --project tests/Api.Tests/Api.Tests.csproj

--parallel <n>

Verteilt die Testklassen jedes Projekts auf n Testprozesse, um schneller aufzuzeichnen. Jeder Prozess führt seine Tests weiterhin einzeln nacheinander aus. Ihre Testsuite muss mehrere gleichzeitige Testprozesse vertragen (keine festen Ports oder gemeinsam genutzten Dateien). Standard: 1.

--no-build

Zeichnet die Ausgabe eines früheren Builds mit derselben Konfiguration auf, statt erneut zu bauen.

dotnet build -c Release
td record -c Release --no-build

td audit

Prüft die Auswahl von {{name}} an Ihrem eigenen Code, so wie wir sie an Open-Source-Repositories prüfen. Es bricht Member Ihres Codes einzeln mit IL-Mutanten (eine Methode wirft, gibt einen Standardwert zurück, nimmt den anderen Zweig, oder ein Feld beginnt mit einem anderen Wert), führt jedes Testprojekt, das die Änderung laden kann, vollständig aus und prüft, dass die Auswahl, die {{name}} für diese Änderung aus Ihren Coverage-Maps trifft, genau wie td test sie trifft, jede fehlgeschlagene Testklasse enthält. Jeder Zweifel zählt gegen {{name}}: Eine Klasse, die die Auswahl ausgelassen hat, läuft erneut allein mit der Änderung und allein ohne sie, bevor sie als Verfehlen zählt, und eine Klasse, die sie ausgeführt hat, zählt erst nach denselben zwei Läufen als erkannt. Ein Testlauf, der mit der Änderung abstürzt oder hängt, läuft erneut ohne sie: Wird der Teil, den die Auswahl ausgelassen hat, nur ohne die Änderung fertig, ist das ein Verfehlen; ein Absturz in dem Teil, den sie ausgeführt hat, zählt nur als erkannt, wenn er wiederkommt. Es braucht keine Lizenz, weil es wie der Shadow-Modus nichts auslässt, und {{name}} selbst macht keinen Netzwerkaufruf; die Builds und Testläufe, die es in der Kopie startet, stellen Pakete wieder her wie Ihre eigenen.

Ihre Quellen und Ihre Build-Ausgabe werden nie geschrieben. {{name}} kopiert den Arbeitsbaum in einen Arbeitsordner (als Copy-on-Write-Klon, wo das Dateisystem das kann), baut und testet dort und löscht den Ordner am Ende, auch nach Strg+C, einem Timeout oder einem Fehler; einen Ordner, den ein abgebrochener Lauf hinterlassen hat, löscht der nächste. Bevor dort etwas gebaut wird, fragt es MSBuild, wohin jedes Projekt schreibt, und startet nicht, wenn etwas davon außerhalb der Kopie liegt, etwa ein absoluter Ausgabepfad. Der Arbeitsbaum darf keine nicht committeten Änderungen haben, weil jede Änderung mit HEAD verglichen wird; wechselt das Repository während des Audits auf einen anderen Commit oder bekommt es Änderungen, hält es mit einem Fehler an. Ein Testprojekt, dessen eigener Filter sich nicht mit einem Klassenfilter verbinden lässt (ein Klassen- oder Abfragefilter von xUnit v3, ein Tree-Node-Filter von TUnit), wird nicht geprüft, und der Bericht nennt den Grund; ebenso Projekte, die das vollständige MSBuild brauchen (ältere Projekte ohne SDK), und Projekte, die in der Kopie nicht bauen, keinen Testbericht schreiben oder im Lauf ohne Änderungen nicht fertig werden. Member von Projekten, die als Source Generator oder Analyzer verwendet werden, bleiben aus der Stichprobe heraus, und der Bericht zählt sie. Projekte auf der Testing Platform werden vor diesem Lauf in der Kopie gebaut, was das Budget bezahlt. Die Member werden in einer festen Reihenfolge genommen, aus einem Hash von Member und Seed, über alle Member gleich: Ob eine Map sagt, dass ein Test einen Member ausgeführt hat, spielt bei der Wahl keine Rolle.

Das Ergebnis nennt die aufgerundete obere 95-%-Schranke der Verfehlensrate und die Zahl der Änderungen, auf der sie beruht; dann die Änderungen, deren Läufe nichts entscheiden konnten (inconclusive) oder die ein Abbruch oder ein Fehler unterbrochen hat (stopped), und die Schranke, wenn jede davon ein Verfehlen wäre:

On your code: 112 changes, 103 broke tests, 0 missed (95% upper bound 2.9%, n = 103); 2 inconclusive, 0 stopped (worst case, counting them as misses: 95% upper bound 5.9%, n = 105); target of 100 reached.
graduation evidence: no: worst case 5.9% > 3.0% because 2 inconclusive and 0 stopped are counted as misses

Die zweite Zeile sagt, ob der Lauf der Beleg ist, den der Abschluss des Shadow-Modus verlangt: mindestens 100 Änderungen, die Tests gebrochen haben, kein Verfehlen und die Schranke im schlimmsten Fall bei höchstens 3,0 %, wie angezeigt. Wenn nicht, nennt sie jede Bedingung, die der Lauf verfehlt ("not yet: 87 changes broke tests, 100 needed", "no: 1 missed"). Ein Lauf mit --member zählt nie, und --target-broken ändert das Kriterium nicht.

Der Bericht (.testdetta/testdetta-audit.json und mit --summary-file die Job-Zusammenfassung) listet jede Änderung mit ihrem Ergebnis. Für ein Verfehlen nennt er die Klasse, die Entscheidungskette, die sie ausgelassen hat (was {{name}} als geändert erkannt hat, wie und warum über das Testprojekt und die Klasse entschieden wurde, den Commit der Map), die Bearbeitung, die Sie von Hand vornehmen, um dieselbe Entscheidung zu sehen, und den Befehl, der diese Änderung allein wiederholt. Exit-Code 3, wenn es ein Verfehlen gibt.

td audit --summary-file "$GITHUB_STEP_SUMMARY" -- -c Release

--target-broken <n>

Hält an, sobald n Änderungen Tests gebrochen haben. Standard: 100; ohne Verfehlen und ohne unentschiedene (inconclusive) oder abgebrochene (stopped) Änderung liegt die obere 95-%-Schranke damit bei 3,0 %, wie angezeigt (2,95 %, aufgerundet).

--max-mutants <n>

Hält an, nachdem n Änderungen Tests ausgeführt haben. Standard: keine Grenze.

--budget <time>

Nach dieser Zeit beginnt keine Änderung mehr. Eine dann noch laufende Änderung läuft innerhalb ihrer eigenen Zeitgrenzen zu Ende und zählt, das Audit kann also um diese Änderung länger dauern, mit --parallel um eine Änderung pro Worker, und eine Änderung macht mehrere Läufe, von denen jeder bis zum Fünffachen des Laufs ihres Projekts ohne Änderungen dauern darf: Sie mittendrin anzuhalten, würde die langsamsten Änderungen verwerfen, und gerade sie sind am häufigsten Verfehlen. Endet das Audit nach dem Budget, sagt der Bericht, um wie viel und welche Änderungen weitergelaufen sind; lassen Sie diesen Spielraum unter der Zeitgrenze eines CI-Jobs. Die <time>-Syntax der Shadow-Grenzen. Standard: 4h.

--parallel <n>

Gleichzeitig getestete Änderungen, jede in ihrer eigenen Kopie des Arbeitsbaums. Jede führt Test-Hosts aus, daher wächst der Speicherbedarf mit n. Standard: 1.

--seed <n>, --kinds <list>, --member <Type.Member>

Der Seed der Reihenfolge (Standard 1); die Arten der Änderung, throw, return-default, flip-branch, field-value oder all (Standard); und, um eine Änderung aus einem Bericht zu wiederholen, der Member, den sie gebrochen hat (für mehrere die Option wiederholen).

--report <path>, --work-dir <dir>

Wohin der JSON-Bericht geht (Standard: .testdetta/testdetta-audit.json) und wohin der Arbeitsordner mit der Kopie kommt (Standard: /tmp, unter Windows der Temp-Ordner). Legen Sie den Arbeitsordner auf die Festplatte des Repositorys, damit die Kopie ein Klon sein kann.

td audit --target-broken 150 --budget 6h --work-dir "$RUNNER_TEMP"

td license

td license status prüft die Lizenz so, wie td test es tun würde, und gibt aus, was sie abdeckt: Lizenznehmer, Seats, aktive Committer der letzten 30 Tage, die Bot-Liste, Scopes und das Enddatum. Es zählt die Committer auf Ihrem Rechner und sendet keine Namen oder E-Mail-Adressen; wie td test kann es die tägliche Lizenzaktualisierung vornehmen, die die Lizenz selbst sendet. td license install <license|file> speichert eine Lizenz in ~/.testdetta/license, für Rechner, auf denen kein CI-Secret sie aufnehmen kann. Siehe Lizenz.

CodeBedeutung
