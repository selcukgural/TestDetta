選択のしくみ

各ステップは、根拠がある場合にのみ選択を絞り込みます。追跡できないものは、多めに実行する側にフォールバックします。

1

プロジェクト

変更されたファイルをプロジェクトに対応付け、ProjectReference をたどります。Directory.Build.props のようなビルド全体に関わるファイルは、その配下のすべてに影響します。

2

シンボル

C# の構文ツリーを比較するため、コメントや空白の編集では何も選択されず、{{name}} はどのメンバーが変更されたかを把握できます。

3

カバレッジ

既定のブランチで記録したマップが、どのテストクラスがどのメソッドを実行したかを示すため、変更されたメソッドから対応するクラスを直接選択できます。

4

名前

新しいコード、フィールド、定数は、テストクラスかマップが把握しているコードに到達するまで、ソース内を名前でたどります。

5

フォールバック

構成ファイル、グローバル using、リフレクションで検出される型など、変更を追跡できない場合はテストプロジェクト全体を実行します。

6

自己チェック

どのテストにも一致しないフィルターは {{name}} のバグとして扱い、フィルターなしでそのプロジェクトを再実行します。

GitHub Actions なら 2 ステップ

既定のブランチへのプッシュごとにカバレッジマップを記録します。プルリクエストでは最新のマップを復元して影響を受けるテストだけを実行し、各クラスが実行された理由やスキップされた理由をジョブサマリーに示します。

GitLab CI、Jenkins、Azure DevOps、Bitbucket →

- if: github.event_name == 'push'
  uses: <owner>/testdetta@<sha>

    mode: record

- if: github.event_name == 'pull_request'
  uses: <owner>/testdetta@<sha>
  with:
    mode: test

ビルドを止めません
