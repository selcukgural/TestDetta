GitHub Actions

既定のブランチのコミットごとにマップを記録し、プルリクエストでは変更が影響するテストだけを実行します。アクションが {{name}} 自体をビルドし、マップを Actions のキャッシュに保持します。

ワークフロー

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  actions: read # lets pull requests find the newest coverage map in the Actions cache

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7 # pin to a commit SHA
        with:
          fetch-depth: 0 # TestDetta compares with the merge base
          persist-credentials: false

      - uses: actions/setup-dotnet@v6 # pin to a commit SHA
        with:
          global-json-file: global.json

      # Also the full test run of main. Leave out projects that cannot run here, such as
      # integration tests that need a database; they are then decided by name on pull requests.
      - if: github.event_name == 'push'
        uses: <owner>/testdetta@<sha>
        with:
          mode: record
          projects: |
            tests/Shop.Tests/Shop.Tests.csproj

      - if: github.event_name == 'pull_request'
        uses: <owner>/testdetta@<sha>
        with:
          mode: test
          dotnet-test-args: --logger trx
          license: ${{ secrets.TESTDETTA_LICENSE }}

完全な履歴が必要です。シャロークローンの場合、アクションはエラーで停止します。fetch-depth: 0 でチェックアウトしてください。

マップがプルリクエストに届くしくみ

  • record モードでは、マップを Actions のキャッシュに testdetta-coverage-<commit> という名前で保存します。プルリクエストはベースブランチのキャッシュを読み取れます。
  • プルリクエストは、マージベースのマップか、マージベースから最大 max-map-age 個の first-parent コミット前までに記録された最新のマップを使用します。
  • 完全に一致しないマップを探すにはリポジトリのキャッシュを一覧表示する必要があり、そのために actions: read が必要です。この許可がない場合はマージベースのマップしか見つからず、ステップがその旨を通知します。
  • マップがまったくなくても mode: test は動作し、名前だけで判断します。

記録中にテストが失敗しても、ジョブが失敗する前にマップは保存されるため、プルリクエストは引き続きマップを利用できます。

アクセス許可

アクセス許可理由
contents: readリポジトリをチェックアウトするため。
actions: readActions のキャッシュを一覧表示し、max-map-age の範囲内で最新のマップを探すため。

persist-credentials: false を指定すると、ジョブの後半でプライベートリポジトリを再びフェッチすることはできません。ただし、fetch-depth: 0 の時点ですべてのブランチを取得しているため、ベースブランチは存在しています。

入力

入力既定値説明
modeプルリクエストでは test（影響を受けるテストを実行）、{{name}} を評価している間のプルリクエストでは shadow（すべてのテストを実行し、選択が除外したはずのものを報告。ライセンス不要）、既定のブランチでは record（カバレッジマップを記録）、スケジュール実行では audit（コピーの中でコードを 1 変更ずつ壊し、失敗したすべてのテストを選択が実行したかを確認。ライセンス不要）。必須です。
basePR のベースブランチtest モードと shadow モードで比較するブランチ。プルリクエスト以外で使う場合は指定してください。
configurationDebugテストのビルドと実行に使うビルド構成。
projectsすべてのテストプロジェクトrecord モード：.csproj のパスを 1 行に 1 つずつ指定します。
parallel1record モード：テストプロジェクトごとのテストホストプロセス数。各プロセスはテストを 1 つずつ実行します。テストスイートが複数のテストプロセスの同時実行に耐えられる必要があります。
no-buildfalserecord モード：true にすると、前のステップで同じ configuration によって作成されたビルドを記録します。
dotnet-test-argstest、shadow、audit モード：dotnet test に渡す追加の引数（スペース区切り）。shadow モードでは、ここにソリューションを指定すると 1 つのコマンドとして実行されます。
max-map-age50test、shadow、audit モード：マップがマージベースより何コミット遅れていてよいか。その間の変更は橋渡しされます。0 を指定すると完全に一致するマップだけを使用します。
drift-fallbackalltest、shadow、audit モード：古いマップ以降の変更にビルドファイル、構成、グローバル using が含まれる場合、all は影響を受けるテストプロジェクトを丸ごと実行し、name は名前で判断します（高速ですが、構成やリフレクションを介した呼び出しは捉えられません）。
shadow-artifact-suffixshadow モード：レポートのアーティファクト名に追加されます。たとえばマトリックスの値を指定すると、マトリックスの各レッグをひと目で区別できます。指定しなくても名前は一意です。
audit-target-broken100audit モード：この数の変更がテストを壊した時点で停止します。
audit-max-mutants制限なしaudit モード：この数の変更がテストを実行した後に停止します。
audit-budget4haudit モード：この時間の経過後は新しい変更を始めません（90s、15m、1h30m。制限なしは none）。ジョブの timeout-minutes より短くしてください。
audit-parallel1audit モード：同時にテストする変更の数。それぞれが専用のコピーで実行され、メモリ使用量はこの数とともに増えます。
github-tokengithub.tokentest、shadow、audit モード：最新のマップを探すために Actions のキャッシュを一覧表示します（actions: read が必要）。
licensetest モード：ライセンス文字列。TESTDETTA_LICENSE のようなリポジトリまたは組織のシークレットから渡します。パブリックリポジトリでは不要です。有効なライセンスがない場合はすべてのテストを実行し、それが原因でジョブが失敗することはありません。shadow モードと audit モードはこれを読み取りません。

シャドウモード

何もスキップせずに {{name}} を試すには、プルリクエストで mode: shadow を使います。コマンドで実行されるすべてのテストが実行され、ジョブの結果はその実行のものになります。ジョブサマリーとレポートのアーティファクトには、選択が実行したはずのテスト、実測の時間、除外したはずの失敗クラスが示されます。アーティファクトの名前は testdetta-shadow-<run>-<attempt>-<job>-… で、ジョブとマトリックスのレッグごとに 1 つ作られ（shadow-artifact-suffix で独自の部分を追加できます）、90 日間保持されます。普段のジョブと同じように 1 つのコマンドとして実行するには、dotnet-test-args にソリューションを指定してください。td test --shadow を参照してください。

ライセンスは不要なので、ライセンスのシークレットは渡されません。また、shadow モードでは {{name}} 自身はネットワーク呼び出しを一切行いません。アクションは test モードと同じように、nuget.org から {{name}} のパッケージをダウンロードし（SHA-512 で検証）、Actions のキャッシュにあるマップを一覧表示して復元します。テストより前のステップでジョブが失敗することはありません。いずれかのステップが自分の役割を果たせない場合（シャローチェックアウト、ダウンロード、ベースブランチの欠落、無効な入力）、または {{name}} がテストの結果なしで終了した場合、そのステップは代わりに同じ引数で通常の dotnet test を実行し、ジョブサマリーにその理由が記載されます。チェックサムが一致しないパッケージが実行されることはありません。レポートのアップロードに失敗しても、ジョブが失敗することはありません。

      - if: github.event_name == 'pull_request'
        uses: <owner>/testdetta@<sha>
        with:
          mode: shadow
          dotnet-test-args: Shop.slnx

スケジュール実行の audit

あなた自身のコードで選択を検証するには、mode: audit をスケジュール実行で使います。たとえば record モードが記録するブランチで週に 1 回です。作業ツリーのコピーの中でコードのメンバーを 1 変更ずつ壊し、各変更を検出できるすべてのテストを実行し、失敗したすべてのテストクラスを選択が実行したかを確認します。td audit を参照してください。チェックアウトとそのビルド出力は読み取られるだけです。ジョブサマリーには判定と、判断の流れを含むすべての見逃しが表示され、アーティファクト testdetta-audit-<run>-<attempt> が JSON レポートを 90 日間保存します。実行するコミットから max-map-age 以内で最新のマップを使用します。ライセンスは不要でネットワーク呼び出しも行わないため、ライセンスのシークレットは渡されません。ランナー上で何時間も実行されるため、ジョブには audit-budget より長い timeout-minutes を設定してください。

on:
  schedule:
    - cron: '0 3 * * 1' # Mondays, 03:00 UTC
  workflow_dispatch:

permissions:
  contents: read

jobs:
  audit:
    runs-on: ubuntu-latest
    timeout-minutes: 300
    permissions:
      contents: read
      actions: read # finds the newest coverage map in the Actions cache
    steps:
      - uses: actions/checkout@v7 # pin to a commit SHA
        with:
          fetch-depth: 0
          persist-credentials: false

      - uses: actions/setup-dotnet@v6 # pin to a commit SHA
        with:
          global-json-file: global.json

      - uses: <owner>/testdetta@<sha>
        with:
          mode: audit
          audit-budget: 4h

テストを壊した変更が 100 個以上あり、見逃しが 1 つもない実行が 1 回あれば、見逃し率の 95% 上限は 3% 未満になります。

ジョブサマリー

test モードでは、{{name}} は選択内容をジョブサマリーに書き込みます。変更されたファイルと比較したベース、各テストプロジェクトがフィルター付きで実行されたか、丸ごと実行されたか、まったく実行されなかったかとその理由、テスト結果、そして関係がある場合はライセンスの状態です。リポジトリ由来のパス、クラス名、理由はコードとして書き込まれるため、プルリクエスト内のファイル名によってページにリンクやメンションが挿入されることはありません。

テストスイートの一部だけを記録する

記録ではテストスイート全体をカバレッジ付きで 1 回実行します。既定のブランチでは、これがそのまま完全なテスト実行にもなります。データベースが必要な統合テストなど、ランナー上で実行できないプロジェクトは projects で除外してください。プルリクエストでは、それらのプロジェクトは名前で判断されます。

前のステップですでに同じ構成でソリューションをビルドしている場合は、no-build: true を設定します。複数のテストプロセスの同時実行に耐えられるテストスイートでは、parallel によって各プロジェクトのテストクラスを指定した数のプロセスに分散できます。
