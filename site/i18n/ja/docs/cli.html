CLI リファレンス

すべてのコマンド、オプション、環境変数について、その動作、既定値、例を示します。簡易版を見るには td --help を実行してください。

td affected [options]              Print the projects and tests a change affects
td test [options] [-- <args>]      Run only the tests a change affects
td record [options]                Run all tests with coverage and store the map
td license status [options]        Check the license and show what it covers
td license install <license|file>  Store a license in ~/.testdetta/license
td audit [options] [-- <args>]     Break your code on purpose and check the selection

すべての分析に共通のオプション

これらは affected、test、record、audit で使用できます。audit は常に HEAD と比較するため、--base は使えません。

--base <ref>

比較対象の git ref です。{{name}} は作業ツリーを、HEAD とこの ref のマージベースと比較します。そのため、ブランチを作成した後にベースブランチに取り込まれたコミットは、ご自身の変更としては数えられません。既定値：origin/main。

td test --base origin/develop
td affected --base HEAD~3      # the last three commits and anything uncommitted

--repo <path>

分析するリポジトリ内の任意のパスです。既定値：カレントディレクトリ。

td affected --repo ../shop

-v、--verbose、--log-level <level>

ログは stderr に出力されるため、stdout は機械可読な状態に保たれます。-v はデバッグログを有効にし、プロジェクトが影響を受ける理由、テストクラスがどのメンバーを実行したか、トレースがどの名前をたどったかなど、すべての判断を説明します。--log-level では trace、debug、information、warning（既定値）、error、none のいずれかを選択できます。trace では git の生の出力も加わります。

td affected -v 2> testdetta-debug.log
td test --log-level information

--max-map-age <n>

マージベース自体にカバレッジマップがない場合に、マージベースから最大 n 個の first-parent コミット前までに記録されたマップを使用します。その間の変更は橋渡しされます。つまり、マップ以降に変更されたメンバーのうち、今回の変更に到達しうるものを実行したクラスも選択されます。0 を指定すると、マージベースで記録されたマップだけを使用します。既定値：50。選択のしくみを参照してください。

td test --max-map-age 20

--drift-fallback <all|name>

古いマップ以降の変更に、ビルドファイル、構成、グローバル using など、メンバー単位で表せないものが含まれる場合の動作を指定します。all（既定値）は影響を受けるテストプロジェクトを丸ごと実行し、name は名前で判断します。後者は高速ですが、構成やリフレクションによってつながった呼び出しは捉えられません。

td test --drift-fallback name

--maps-dir <dir>

カバレッジマップをリポジトリの外に、コミットごとに 1 フォルダーで保持します。record は <dir>/<commit>/ に保存し、affected と test は --max-map-age の範囲内で最新のものを復元します。GitHub Actions 以外の CI システムで、共有ディスクまたは同期したオブジェクトストレージとともに使用します。既定値：マップはリポジトリ内の .testdetta/coverage に置かれます。

td record --maps-dir /srv/testdetta-maps/shop
td test --base origin/main --maps-dir /srv/testdetta-maps/shop

td affected

何もビルドや実行をせずに、変更が何に影響するかをその理由とともに出力します。

--format <text|json|paths|commands>

形式出力用途
text（既定値）影響を受けるプロジェクトとその理由、続いてテスト計画人が読む
jsonすべてのプロジェクトとテストクラスについて、判断、根拠、推定時間スクリプト、ダッシュボード
paths影響を受けるテストの .csproj を 1 行に 1 つ別のツールへの入力
commandsテストプロジェクトごとに 1 つの dotnet test コマンド（フィルター付き）独自の方法でのテスト実行
 
td affected --format json > plan.json
td affected --format paths | xargs -n1 dotnet build

--tests-only

影響を受けるテストプロジェクトだけを一覧表示し、途中にある本番コードのプロジェクトは含めません。

--build

変更がリポジトリ内のソースジェネレーターに及ぶ場合、それを使うテストプロジェクトをビルドし、生成されたコードをカバレッジマップと比較します。td test は常にこれを行います。このオプションがない場合は、ソースより新しい既存のビルドを読み込みます。そのようなビルドがなければ、それらのテストプロジェクトはすべて実行するものとして表示されます。

td test

影響を受けるテストだけをビルドして実行します。一部のクラスだけが影響を受ける場合はテストプロジェクトごとにフィルターを使い、すべてのクラスが影響を受ける場合や変更を絞り込めない場合はプロジェクト全体を実行し、どのクラスも影響を受けない場合は何も実行しません。いずれかのテストが失敗すると、終了コードは 3 になります。変更がリポジトリ内のソースジェネレーターに及ぶ場合は、それを使うテストプロジェクトを先にビルドし、変更された生成コードだけを変更として扱います。ビルドが失敗した場合は、コンパイラのエラーを表示してここで停止します。

--dry-run

dotnet test コマンドを実行せずに出力します。global.json がサブフォルダーにあるプロジェクトは、(cd src && dotnet test ...) のように出力されます。

--summary-file <path>

Markdown のサマリーを追記します。内容は、各プロジェクトの結果、実行されたクラスとその理由、スキップされたクラス、記録済みのテスト時間のうち節約できた分です。GitHub Actions では $GITHUB_STEP_SUMMARY を指定します（アクションが自動的に行います）。例をご覧ください。

td test --summary-file "$GITHUB_STEP_SUMMARY"

--shadow

何もスキップせずに {{name}} を試すためのシャドウモードです。ライセンスは不要で、このモードでは {{name}} 自身はネットワーク呼び出しを一切行いません。ライセンスの読み取りや更新は行われず、何も送信されません。ビルドはいつもどおりパッケージを復元し、ベースコミット上の再実行も通常のビルドと同じようにそのコミットのパッケージを復元します。あなた自身の -- 引数で実行されるすべてのテストが実行され、終了コードはその実行のものになります。引数がソリューション（.sln、.slnx、.slnf）、1 つのプロジェクト、ディレクトリを指定している場合、または何も指定していない場合（作業ディレクトリにある唯一のソリューションまたはプロジェクト）、{{name}} はその 1 つの dotnet test コマンドを作業ディレクトリでそのまま実行し、プロジェクトごとのテストレポートの指定だけを追加します。VSTest では --logger trx（TRX ロガーを自分で指定している場合を除く）、Testing Platform ではそのレポートオプションです。結果ディレクトリ、ロガー、実行が書き出すファイルはそのまま残ります。{{name}} はレポートを出力された場所で読み取り、コピーします。削除するのは、{{name}} 自身が要求したレポート（あなたが独自の TRX ロガーやレポートオプションを指定していない場合）だけで、読み取った後に削除します。それ以外の場合、たとえば実行すべきソリューションが 1 つに定まらない場合や 2 つのテストプロジェクトが同じ名前のアセンブリをビルドする場合は、コマンドが実行する各テストプロジェクトを同じディレクトリから 1 つずつ順に実行し、その理由をレポートに記載します。コマンドが実行するテストプロジェクトを特定できない場合は、そのディレクトリの下にあるすべてのテストプロジェクトを実行し、そのこともレポートに記載します。

テストの実行前に {{name}} が失敗した場合、コマンドは {{name}} なしで指定どおりに実行されます。実行後に失敗した場合も、終了コードはその実行のものです。いずれの場合も、レポートにシャドウ結果がない理由が記載されます。その後 {{name}} は、実行結果を自分が選択したはずのテストとテストごとに比較し、除外したはずの失敗クラスをそれぞれ再実行します。まず変更ありで単独実行し、単独で成功した場合は、完全実行と同じようにそのプロジェクトの他のクラスと一緒に実行します（そこで成功すれば不安定、再び失敗すれば順序依存です）。次に、別のチェックアウトでベースコミット上で同じように実行します。変更ありで失敗するすべてのテストがそこでも失敗すれば変更が原因ではなく、1 つでもそこで成功すれば見逃しです。再実行できなかったクラスは、確認されるまで見逃しとして扱われます。再実行はレポートを {{name}} 自身の一時フォルダーにだけ書き出します。再実行によりジョブが長くなることがありますが、最大でも分類の予算の分だけです。Ctrl+C やジョブのキャンセルでテストは停止され、その一時フォルダーとベースのチェックアウトは削除されます。

完全実行が終わるまで、選択に関する情報は何も表示されません。また、判断が表示されるのはこのジョブで実行されたクラスだけです。フィルターで除外されたクラスは判断なしで「実行されなかった」と記載され、その場合はプロジェクト自体の判断も表示されません。合計には実行されたものだけが数えられます。レポートには、まず実行全体の実測時間を含む判定、次に実行の方法、各クラスの判断と結果、プロジェクトごとの実測時間と選択が実行したはずの部分の比較、そしてライセンスなしで結果を再現するために必要な情報（{{name}} のバージョンと SHA-256、コミット、カバレッジマップとそのハッシュ、同じ td test --shadow コマンド）が含まれます。

制限事項：レポートはリポジトリの下と結果ディレクトリで探されるため、run settings でリポジトリの外に設定された結果ディレクトリは読み取られません。ベースのチェックアウトはリポジトリの外の一時フォルダーに置かれるため、リポジトリのルートより上にあるファイル（親フォルダーにある Directory.Build.props、global.json、NuGet.config）はそこでは参照されません。ベースでの再実行がビルドできないクラスは未分類として報告されます。

td test --shadow --summary-file "$GITHUB_STEP_SUMMARY" -- MySolution.sln -c Release

--shadow-no-classify

選択が除外した失敗クラスを再実行しません。その場合、それらは未分類として報告されます。

--shadow-report <path>

JSON レポートの出力先です。既定値: リポジトリ内の .testdetta/testdetta-shadow.json。

--shadow-analysis-timeout <time>

テストの前に行う {{name}} の分析にかけられる最長時間です。既定値: 10m。これを超えると分析は停止され、すべてのテストはそのまま実行され、レポートにシャドウ結果がない理由が記載されます。

--shadow-rerun-timeout <time>, --shadow-rerun-idle-timeout <time>

変更ありでの 1 回の再実行にかけられる最長時間と、そのプロセスがほとんど CPU を使わない状態が続いたときに停止と見なして止めるまでの時間です。既定値: 15m と 5m。停止された再実行のクラスは未分類として報告されます。

--shadow-base-timeout <time>, --shadow-base-idle-timeout <time>

ベースコミット上の再実行について同じものを指定します。こちらはまずそのチェックアウトで復元とビルドを行います。既定値: 30m と 10m。復元は CPU がほぼ止まったままネットワークを待つため、アイドル制限が長くなっています。

--shadow-classify-budget <time>

分類全体にかけられる最長時間です。すべての再実行とベースのチェックアウトを合わせた時間です。既定値: 45m。実行中の再実行は予算が尽きた時点で停止され、それまでに分類されなかった失敗は理由とともに未分類として報告されます。完全実行と終了コードが影響を受けることはありません。レポートには、使用された制限と予算のうち消費した時間が表示されます。

<time> は 90s、15m、1h、1h30m の形式で、最大 168h です。数字だけの場合は分を意味し、0 または none は制限なしを意味します。GitHub Action では、同じ名前の入力（shadow-analysis-timeout、shadow-rerun-timeout、shadow-classify-budget など）で設定します。

td test --shadow --shadow-classify-budget 20m --shadow-base-timeout none

-- <dotnet test arguments>

-- の後に指定したものはすべて、各 dotnet test の呼び出しに渡されます。独自の --filter はそのまま生かされます。{{name}} はそれを自身のクラスフィルターと結合するため、選択されたテストのうちフィルターに合うものだけが実行されます。xUnit v3 の trait、method、namespace フィルターも同じように選択を絞り込みます。ランナーがクラスフィルターと結合できないフィルター（xUnit v3 の class フィルターや query フィルター、TUnit の tree-node フィルター）を指定した場合、そのプロジェクトはあなたのフィルターの下ですべて実行されます。シャドウモードでは、これがあなた自身のテストコマンドになります。--shadow を参照してください。

td test -- -c Release --logger trx
td test -- --no-restore
td test -- --filter "Category!=Integration"

td record

すべてのテストをカバレッジ付きで実行し、テストプロジェクトごとに 1 つのマップを .testdetta/coverage（または --maps-dir）に書き込みます。既定のブランチで実行してください。これはそのブランチの完全なテスト実行も兼ねます。テストが失敗すると終了コードは 3 になりますが、マップは書き込まれ、失敗したクラスは以後常に選択されます。

-c、--configuration <name>

ビルド構成です。既定値：Debug。

-f、--framework <tfm>

複数のターゲットフレームワークを持つテストプロジェクトで記録するターゲットフレームワークです。既定値：このマシンで実行できる、プロジェクトの最初のターゲットフレームワーク（.NET Framework は Windows のみ）。

td record -f net10.0

--project <path>

このテストプロジェクトだけを記録します。パスはリポジトリのルートからの相対パスで、複数指定する場合は繰り返します。データベースが必要な統合テストなど、CI で実行できないプロジェクトは除外してください。それらは名前で判断されます。

td record --project tests/Shop.Tests/Shop.Tests.csproj --project tests/Api.Tests/Api.Tests.csproj

--parallel <n>

記録を高速化するため、各プロジェクトのテストクラスを n 個のテストプロセスに分散します。各プロセスはテストを 1 つずつ実行します。テストスイートが複数のテストプロセスの同時実行に耐えられる必要があります（固定ポートや共有ファイルを使わないこと）。既定値：1。

--no-build

再ビルドせずに、同じ構成で事前に行ったビルドの出力を記録します。

dotnet build -c Release
td record -c Release --no-build

td audit

私たちがオープンソースのリポジトリで行っているのと同じ方法で、あなた自身のコードで {{name}} の選択を検証します。IL ミュータント（メソッドが例外を投げる、既定値を返す、もう一方の分岐に進む、フィールドが別の値で始まる）を使ってコードのメンバーを 1 つずつ壊し、その変更を読み込めるすべてのテストプロジェクトを完全に実行し、{{name}} がその変更に対してカバレッジマップから（td test とまったく同じように）行う選択に、失敗したすべてのテストクラスが含まれているかを確認します。疑わしい場合はすべて {{name}} に不利に数えます。選択から除外されたクラスは、見逃しと数える前に、変更ありで単独実行し、さらに変更なしで単独実行します。選択が実行したクラスも、同じ 2 回の実行を経て初めて検出と数えます。変更ありでクラッシュまたはハングしたテスト実行は、変更なしで再実行します。選択が除外した部分が変更なしでのみ完了する場合、それは見逃しです。選択が実行した部分でのクラッシュは、再び起きた場合にのみ検出と数えます。ライセンスは不要で、ネットワーク呼び出しも一切行いません。シャドウモードと同じく、何もスキップしないからです。

ソースとビルド出力には一切書き込みません。{{name}} は作業ツリーを作業フォルダーにコピーし（ファイルシステムが対応していればコピーオンライトのクローンとして）、そこでビルドとテストを行い、最後にフォルダーを削除します。Ctrl+C、タイムアウト、エラーの後も同様です。強制終了された実行が残したフォルダーは次回の実行が削除します。そこで何かをビルドする前に、各プロジェクトがどこに書き込むかを MSBuild に問い合わせ、その一部でもコピーの外にある場合（絶対パスの出力先など）は開始しません。すべての変更は HEAD と比較されるため、作業ツリーにコミットされていない変更があってはいけません。監査の実行中にリポジトリが別のコミットに移ったり変更が加わったりした場合は、エラーで停止します。独自のフィルターをクラスフィルターと組み合わせられないテストプロジェクト（xUnit v3 のクラスフィルターやクエリフィルター、TUnit の tree-node フィルター）は監査せず、その理由をレポートに記載します。メンバーは、メンバーとシード値のハッシュから決まる固定の順序で、すべてのメンバーから等しく選ばれます。マップがそのメンバーをどれかのテストが実行したと示しているかどうかは、選び方に一切関係しません。

結果には、切り上げた見逃し率の 95% 上限と、その根拠となる変更の数が示されます。続いて、実行結果から判定できなかった変更（inconclusive）、キャンセルやエラーで中断された変更（stopped）と、それらがすべて見逃しだった場合の上限が示されます。

On your code: 112 changes, 103 broke tests, 0 missed (95% upper bound 2.9%, n = 103); 2 inconclusive, 0 stopped (worst case, counting them as misses: 95% upper bound 5.9%, n = 105); target of 100 reached.

レポート（.testdetta/testdetta-audit.json、および --summary-file を指定した場合はジョブサマリー）には、すべての変更とその結果が記載されます。見逃しについては、クラス、それを除外した判断の流れ（{{name}} が何の変更を検出したか、テストプロジェクトとクラスがどのように、なぜ判断されたか、マップのコミット）、同じ判断を確認するために手で行う編集、その変更だけを再実行するコマンドが示されます。見逃しがあると終了コードは 3 です。

td audit --summary-file "$GITHUB_STEP_SUMMARY" -- -c Release

--target-broken <n>

n 個の変更がテストを壊した時点で停止します。既定値：100。見逃しがなければ、95% 上限が 3.0% 以下になります。

--max-mutants <n>

n 個の変更がテストを実行した後に停止します。既定値：制限なし。

--budget <time>

この時間が経過した後は新しい変更を始めません。その時点で実行中の変更は、自身の時間制限の範囲で最後まで実行され、数えられます。そのため、監査はその変更の分だけ長くかかることがあります。<time> の書式はシャドウの制限と同じです。既定値：4h。

--parallel <n>

同時にテストする変更の数です。それぞれが作業ツリーの専用コピーで実行されます。それぞれがテストホストを実行するため、メモリ使用量は n とともに増えます。既定値：1。

--seed <n>, --kinds <list>, --member <Type.Member>

順序のシード値（既定値 1）、変更の種類（throw、return-default、flip-branch、field-value、または既定値の all）、そしてレポートの変更を再現するための、その変更が壊したメンバー（複数の場合はオプションを繰り返します）。

--report <path>, --work-dir <dir>

JSON レポートの出力先（既定値：.testdetta/testdetta-audit.json）と、コピーを置く作業フォルダーの場所（既定値：/tmp、Windows では一時フォルダー）です。コピーをクローンにできるよう、作業フォルダーはリポジトリと同じディスクに置いてください。

td audit --target-broken 150 --budget 6h --work-dir "$RUNNER_TEMP"

td license

td license status は、td test と同じ方法でライセンスを確認し、ライセンシー、シート数、過去 30 日間のアクティブなコミッター、ボットの一覧、スコープ、終了日といった対象範囲を出力します。個人データをどこかに送信することはありません。td license install <license|file> はライセンスを ~/.testdetta/license に保存します。CI のシークレットにライセンスを保持できないマシン向けです。ライセンスを参照してください。
