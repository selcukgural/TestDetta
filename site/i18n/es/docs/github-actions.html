GitHub Actions

Registra un mapa por cada commit de la rama predeterminada y deja que las pull requests ejecuten solo las pruebas que sus cambios afectan. La acción obtiene de nuget.org el paquete de {{name}} que fija en tool.lock, comprueba su SHA-512 antes de ejecutarlo y guarda los mapas en la caché de Actions.

Workflow

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  actions: read # lets pull requests find the newest coverage map in the Actions cache

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7 # pin to a commit SHA
        with:
          fetch-depth: 0 # TestDetta compares with the merge base
          persist-credentials: false

      - uses: actions/setup-dotnet@v6 # pin to a commit SHA
        with:
          global-json-file: global.json

      # Also the full test run of main. Leave out projects that cannot run here, such as
      # integration tests that need a database; they are then decided by name on pull requests.
      - if: github.event_name == 'push'
        uses: <owner>/testdetta@<sha>
        with:
          mode: record
          projects: |
            tests/Shop.Tests/Shop.Tests.csproj

      - if: github.event_name == 'pull_request'
        uses: <owner>/testdetta@<sha>
        with:
          mode: test
          dotnet-test-args: --logger trx
          license: ${{ secrets.TESTDETTA_LICENSE }}

Se necesita el historial completo. En los modos test, record y audit, la acción se detiene con un error en un clon superficial (shallow); el modo sombra avisa y ejecuta en su lugar tu dotnet test normal. Haz el checkout con fetch-depth: 0.

Cómo llegan los mapas a las pull requests

  • El modo record guarda los mapas en la caché de Actions con la clave testdetta-coverage-<commit>. Las pull requests pueden leer las cachés de su rama base.
  • Una pull request usa el mapa de su merge base, o el más reciente registrado hasta max-map-age commits de primer padre (first-parent) antes de ella.
  • Para encontrar ese mapa más reciente que no es exacto se listan las cachés del repositorio, lo que requiere actions: read. Sin ese permiso, solo se encuentra un mapa en la merge base, y el paso lo indica con un aviso.
  • Sin ningún mapa, mode: test sigue funcionando y decide solo por nombre.

Cuando fallan pruebas durante el registro, el mapa se guarda igualmente antes de que falle el job, así que las pull requests siguen teniendo un mapa con el que trabajar.

Permisos

PermisoPor qué
contents: readHacer el checkout del repositorio.
actions: readListar las cachés de Actions para encontrar el mapa más reciente dentro de max-map-age.

Con persist-credentials: false, un repositorio privado no se puede volver a descargar más adelante en el job; fetch-depth: 0 ya trae todas las ramas, así que la rama base está disponible.

Modo sombra

Para probar {{name}} sin omitir nada, use mode: shadow en las pull requests. Todas las pruebas que ejecuta su comando se ejecutan, y el resultado del job es el de esa ejecución; el job summary y el artefacto del informe muestran lo que habría ejecutado la selección, los minutos medidos y cada clase fallida que habría dejado fuera. El artefacto se llama testdetta-shadow-<run>-<attempt>-<job>-…, uno por job y por parte de la matriz (shadow-artifact-suffix añade su propia parte), y se conserva hasta 90 días (el ajuste de retención de artefactos de su repositorio puede acortarlo). Nombre su solución en dotnet-test-args para ejecutarla como un solo comando, como hace su propio job; vea td test --shadow.

No necesita licencia, así que no se le pasa el secreto de la licencia, y el propio {{name}} no hace ninguna llamada de red en modo sombra. La acción descarga el paquete de {{name}} desde nuget.org (comprobado con su SHA-512) y lista y restaura los mapas de su caché de Actions, como en el modo test. Ningún paso anterior a las pruebas hace fallar el job: si uno no puede hacer su parte (un checkout superficial, la descarga, una rama base que falta, una entrada no válida), o {{name}} termina sin un resultado de las pruebas, el paso ejecuta en su lugar su dotnet test normal con los mismos argumentos, y el job summary dice por qué. Un paquete que no coincide con su suma de comprobación nunca se ejecuta. Una subida fallida del informe tampoco hace fallar nunca el job.

      - if: github.event_name == 'pull_request'
        uses: <owner>/testdetta@<sha>
        with:
          mode: shadow
          dotnet-test-args: Shop.slnx

Los proyectos de prueba de Microsoft.Testing.Platform necesitan un paso más. {{name}} lee la opción de informe que acepta un proyecto así a partir de su salida de compilación, porque una opción que el proyecto no conoce haría fallar su ejecución, y no la deduce de las referencias de paquetes. En un checkout recién hecho todavía no hay salida de compilación: los proyectos se ejecutan entonces uno a uno sin informe, y el informe nombra cada uno con "no test report: the project was not built before the run", así que sus fallos no se pueden comparar con la selección. Compile primero, con la misma configuración, y pase --no-build:

      - if: github.event_name == 'pull_request'
        run: dotnet build Shop.slnx -c Debug

      - if: github.event_name == 'pull_request'
        uses: <owner>/testdetta@<sha>
        with:
          mode: shadow
          configuration: Debug
          dotnet-test-args: Shop.slnx --no-build

Audit programado

Para comprobar la selección en tu propio código, usa mode: audit de forma programada, por ejemplo cada semana en la rama que registra el modo record. Rompe miembros de tu código cambio a cambio en una copia del árbol de trabajo, ejecuta cada prueba que puede ver cada cambio y comprueba que la selección ejecutó cada clase de prueba que falló; consulta td audit. Tu checkout y su salida de compilación solo se leen. El resumen del job muestra el veredicto y cada fallo no detectado con su cadena de decisiones; el artefacto testdetta-audit-<run>-<attempt> guarda el informe JSON hasta 90 días. Usa el mapa más reciente dentro de max-map-age del commit en que se ejecuta. No necesita licencia, así que no se le pasa el secreto de la licencia, y el propio {{name}} no hace ninguna llamada de red: la acción descarga el paquete y encuentra los mapas como en el modo test, y las compilaciones en la copia restauran paquetes como las tuyas. Se ejecuta durante horas en tus runners: dale al job un timeout-minutes bastante mayor que audit-budget, porque un cambio que aún se ejecuta cuando se agota el presupuesto termina primero (todas sus ejecuciones, que pueden durar varias veces la ejecución completa de los proyectos de prueba que lo cargan); el resumen dice entonces cuánto se pasó el audit del presupuesto y qué cambios siguieron ejecutándose. Un job detenido al agotar su tiempo límite informa el cambio que interrumpió como stopped.

on:
  schedule:
    - cron: '0 3 * * 1' # Mondays, 03:00 UTC
  workflow_dispatch:

permissions:
  contents: read

jobs:
  audit:
    runs-on: ubuntu-latest
    timeout-minutes: 360 # the most a GitHub-hosted runner allows: 2 h of headroom after audit-budget
    permissions:
      contents: read
      actions: read # finds the newest coverage map in the Actions cache
    steps:
      - uses: actions/checkout@v7 # pin to a commit SHA
        with:
          fetch-depth: 0
          persist-credentials: false

      - uses: actions/setup-dotnet@v6 # pin to a commit SHA
        with:
          global-json-file: global.json

      - uses: <owner>/testdetta@<sha>
        with:
          mode: audit
          audit-budget: 4h

La graduación del modo sombra pide una ejecución del audit con al menos 100 cambios que rompieron pruebas, ningún fallo no detectado y un límite superior del 95 % de la tasa de fallos no detectados en el peor caso de como mucho el 3,0 %: el peor caso cuenta como fallo no detectado cada cambio cuyas ejecuciones no permitieron decidir (inconclusive) o que se interrumpió (stopped), y el límite se muestra redondeado hacia arriba. El resumen y el informe dicen en una línea si la ejecución lo cumple y, si no, por qué, por ejemplo "not yet: 87 changes broke tests, 100 needed" o "no: worst case 4.1% > 3.0% because 5 inconclusive and 0 stopped are counted as misses". Una ejecución limitada a algunos miembros con --member nunca cuenta.

Job summary

En el modo test, {{name}} escribe su selección en el job summary: los archivos modificados y la base con la que comparó, cada proyecto de pruebas indicando si se ejecutó filtrado, completo o no se ejecutó y por qué, los resultados de las pruebas y el estado de la licencia cuando importa. Las rutas, los nombres de clase y los motivos procedentes del repositorio se escriben como código, para que los nombres de archivo de una pull request no puedan inyectar enlaces ni menciones en la página.

Registrar solo una parte del conjunto de pruebas

El registro ejecuta una vez todo el conjunto de pruebas con cobertura, lo que en la rama predeterminada es también tu ejecución completa de pruebas. Excluye con projects los proyectos que no pueden ejecutarse en el runner, como las pruebas de integración que necesitan una base de datos. Las pull requests deciden entonces esos proyectos por nombre.

Si un paso anterior ya compiló la solución con la misma configuración, define no-build: true. Para un conjunto de pruebas que tolera varios procesos de prueba a la vez, parallel reparte las clases de prueba de cada proyecto entre esa cantidad de procesos.
